# ADR 0013: Tutorial/verification data commit policy -- figures and summary CSVs only, not raw snapshot data

**Status:** Accepted
**Date:** 2026-10-14

## Context

This repository's tutorials (`tutorials/*/`) write two different kinds
of output when run: small, scriptable derived quantities (an L1 error,
a contact width, a measured wave speed, a final mass -- one row per
resolution/flux in a `data/.../summary.csv`) and large, per-snapshot raw
field dumps (ASCII legacy VTK frames, one file per output time per
field per block). The forward-facing-step tutorials
(`tutorials/euler_2d_forward_step/`, `tutorials/euler_3d_forward_step_extrusion/`,
task 0010) were the first to produce enough of the latter to matter --
dozens of `.vtk` frames per resolution/flux combination, repeated across
several resolutions -- and picked up an ad hoc `.gitignore` rule
(`tutorials/euler_2d_forward_step/data/**/*.vtk`,
`tutorials/euler_3d_forward_step_extrusion/data/**/*.vtk`) to keep them
out of version control, with a code comment explaining the reasoning
but no stated repo-wide policy. Every tutorial added since (Shu-Osher,
propagating shock, task 0012/0013) has, in practice, followed the same
pattern without it ever being written down as a decision -- Amelia's
PR #6 review flagged this as needing an explicit decision rather than
staying an incidental `.gitignore` comment specific to one tutorial, so
a future tutorial does not have to independently re-derive the same
choice (or, worse, commit a large VTK dataset before anyone notices).

## Options considered

### Option A (selected): commit only `figures/*.png` and `data/*/summary.csv`; gitignore raw snapshot data repo-wide

Every tutorial/verification case commits its rendered figures
(`figures/*.png`, already how every tutorial's qualitative result is
actually consumed -- READMEs embed and discuss these, not the raw
frames) and its derived-metric summary table(s)
(`data/**/summary.csv` and, where a tutorial also writes one-row-per-
case detail files like `tutorials/euler_1d_sod_shock_tube/data/case_*.csv`,
those too -- anything that is itself a small table of scalars, not a
per-cell field dump). Raw per-snapshot field data (VTK frames, or any
future equivalent format) is never committed; it is regenerated by
re-running the tutorial, exactly as the forward-step tutorials already
do.

Advantages:
- Matches what every verification test in this repository already
  does for correctness checking (`VERIFICATION.md`'s "Canonical
  problems with no closed-form exact solution" section): compare
  against a known analytic value or a converged-reference derived
  metric, never a raw field dump. A committed `summary.csv` is exactly
  that oracle/reference value, machine-readable and diffable in a PR;
  a committed raw VTK frame is not a check of anything by itself --
  someone has to open it in a viewer and look.
- Keeps repository size bounded and predictable as more tutorials are
  added. `BENCHMARKS.md` #10 already makes the analogous call for
  benchmark data ("raw machine-readable benchmark results... under a
  dedicated benchmark-results directory that is not necessarily
  committed for every local run... accepted reference baselines should
  be version-controlled"); this ADR makes the same kind of call for
  tutorial/verification data, rather than leaving tutorials to
  independently reinvent it per case.
- No new infrastructure needed. Per Amelia's review: nothing in this
  repository's current tutorial set is large enough to justify external
  data storage (an object store, Git LFS, a separate data repository);
  a committed-size discipline plus the derived-metric-oracle pattern
  already established is sufficient at this scale. Revisit only if a
  future case's raw data genuinely needs to be reproduced exactly
  (not just regenerated and re-checked against its own summary metrics)
  -- no current case needs that.

Disadvantages:
- A reader cloning the repository cannot immediately view a prior run's
  raw field frames without re-running the tutorial themselves (typically
  seconds to low minutes for this repository's current case sizes, see
  each tutorial's own README for measured wall-clock). Mitigated: the
  committed `figures/*.png` already show the qualitative result the
  frames would be used for, and the README explains it in text.

### Option B: commit everything, including raw VTK frames

Disadvantages (why rejected): this is what the forward-step tutorials
did before their own `.gitignore` fix (task 0010) -- unbounded repo
growth as more tutorials/resolutions are added, large binary diffs on
every regeneration, and no actual verification value added over the
derived-metric summary (nobody re-opens an old VTK frame to check
correctness; the tests do that numerically). Already recognized as a
problem once; this ADR is what stops it recurring per-tutorial.

### Option C: external data-storage infrastructure (Git LFS, object storage, a separate data repository)

Disadvantages (why rejected, for now): real infrastructure and process
overhead (a new dependency, credentials/access for contributors,
retrieval tooling) for a problem this repository does not have yet --
every current tutorial's full raw dataset is small enough to regenerate
in seconds to low minutes (see e.g. `tutorials/euler_2d_forward_step/README.md`'s
measured per-resolution wall-clock times). Revisit if a future case
(e.g. a large 3D reacting-flow or AMR run, ROADMAP.md's later phases)
produces raw data expensive enough that regeneration-on-demand is no
longer practical.

## Decision

**Going forward, every tutorial/verification case commits only
`figures/*.png` and `data/**/summary.csv` (plus any other small,
scriptable, per-case-row CSV of derived scalars under `data/`) -- never
raw per-snapshot field data (VTK frames or any future equivalent
format).** This formalizes, as an explicit repo-wide policy, the
pattern the forward-step tutorials' `.gitignore` rule already
established in practice; new tutorials should follow it without needing
their own per-tutorial `.gitignore` addition or their own independent
re-derivation of the same choice.

`.gitignore` is generalized from the two forward-step-specific patterns
to one repo-wide rule (`tutorials/*/data/**/*.vtk`) covering every
tutorial's `data/` directory, present and future, rather than requiring
each new tutorial to add its own line.

**This does not retroactively untrack already-committed VTK frames.**
`tutorials/euler_3d_forward_step_extrusion/data/` still has ~34 `.vtk`
frames committed from before this ADR (and the forward-step
`.gitignore` comment it formalizes already said as much: "Historical
VTK frames already committed in prior commits are a separate cleanup
question, not addressed by this ignore rule"). Removing already-tracked
files is a separate, more invasive decision (rewriting what a later
clone/checkout contains) that nobody has asked for and that this ADR
does not make -- flagged here as a known, accepted inconsistency rather
than silently left unexplained.

## Consequences

**Easier:** a future tutorial author has one clear, stated rule to
follow instead of having to notice and copy the forward-step precedent;
reviewers have an explicit policy to check a PR against instead of
judgment-calling it per tutorial.

**Harder:** nothing new -- this is what the forward-step tutorials
already did in practice; this ADR only makes it explicit and
repo-wide.

**Future constraint:** if a future canonical case (e.g. a large 3D
reacting-flow or AMR demonstration, per `ROADMAP.md`'s later phases)
needs its raw data actually preserved rather than regenerated-on-demand,
that is a new requirement this ADR's Option C explicitly anticipates and
defers -- it should be its own ADR amendment when that need is real, not
assumed now.

## Revisit criteria

- A future case whose raw snapshot data takes long enough to regenerate
  (e.g. requires real GPU/cluster time, not a local few-minutes run)
  that "re-run it" is no longer a practical substitute for "it was
  committed" -- would justify Option C (external data-storage
  infrastructure).
- A concrete request to reproduce a prior run's exact raw field data
  (not just its derived metrics) -- would justify revisiting the
  "no retroactive untracking" position above for the specific files in
  question.
